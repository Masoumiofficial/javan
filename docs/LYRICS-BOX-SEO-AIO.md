# آنالیز باکس «متن ترانه» — از نگاه UX، SEO، GEO و AIO

**تاریخ:** ۲۰۲۶-۱۰-۱۵ · **دامنه:** قالب موسیقی (TaranehYar / javanseda) · **فیلد منبع:** `music_text`

## ۱) خلاصهٔ مدیریتی — نظر من در چند خط

1. **ایدهٔ شما درست است.** متن ترانه باید از «یک پاراگراف وسط صفحه» به یک **بخش مستقل با تیتر، هویت بصری و داده‌ساختاریافته** تبدیل شود؛ همین حالا هم در قالب فقط یک `div.music_textss` با `text-align:center` است، بدون تیتر و بدون هیچ نشانی برای موتور جست‌وجو و مدل‌های زبانی.
2. **بیشترین سود از تیتر می‌آید، نه از اسکیما.** تیتر `متن آهنگ {song} از {artist}` دقیقاً همان الگویی است که کاربر جست‌وجو می‌کند. این کار **بدون هیچ ریسکی** بیشترین بازده را دارد.
3. **داده‌ساختاریافته لازم است ولی انتظار ریچ‌رزالت نداشته باشید.** گوگل برای «متن ترانه» ریچ‌رزالت ندارد؛ ارزش اسکیما اینجا در **درک موجودیت (entity)** و **استنادپذیری در پاسخ‌های هوش مصنوعی** است، نه در ظاهر SERP.
4. **برای GEO/AIO، متنِ قابلمشاهده در HTML مهم‌تر از JSON-LD است.** خزنده‌های مدل‌های زبانی عمدتاً بدنهٔ HTML را می‌خوانند؛ پس متن ترانه نباید داخل تصویر، کاروسل، `display:none` یا فقط با جاوااسکریپت باشد.
5. **یک ریسک واقعی داریم: جای باکس.** متن ترانه بلند است و اگر بالای پخش‌کننده و لینک‌های دانلود باشد، کاربر «قصد دانلود» را معطل می‌کند. برای همین یک سوئیچ یک‌خطی گذاشتم تا بدون جابه‌جا کردن کد، باکس را بالا/پایین ببرید.
6. **و یک هشدار حقوقی/کیفیتی:** بازنشر کامل متن ترانه در بسیاری از کشورها موضوع حق نشر است و در سئو هم «محتوای تکراری» است چون همهٔ سایت‌های متن ترانه همان متن را دارند. مزیت رقابتی صفحهٔ شما **صدا، توضیحات و لینک دانلود** است؛ متن ترانه باید مکمل باشد، نه تنها محتوای صفحه.

## ۲) وضعیت فعلی کد (قبل از تغییر)

```php
<div class="music_textss">
<?php echo wp_kses_post( get_field( 'music_text' ) ); ?>
<div class="clear"></div>
</div>
```

```css
.music_textss{text-align:center;}
```

مشکل‌ها: بدون تیتر (H2/H3)، بدون `lang`/`dir`، بدون لینک به صفحهٔ خواننده، بدون داده‌ساختاریافته، بدون کنترل طول خط، بدون حالت شب اختصاصی، بدون امکان کپی/اشتراک، و بدون هیچ تفکیک بصری از متن توضیحات.

## ۳) آنچه پیاده‌سازی شد

| مورد | جزئیات | چرا |
|---|---|---|
| تیتر هدف‌دار | `<h2>متن آهنگ {song} از {artist}</h2>` با fallback به عنوان نوشته | هم‌راستا با الگوی جست‌وجوی کاربر و ساختار هدینگ صفحه (H1 عنوان نوشته → H2 متن آهنگ) |
| جعبهٔ مستقل و «شیک» | `section.music_lyrics_box` با هدر گرادیانی، گوشهٔ گرد ۱۲px، سایه، آی‌کون، هم‌خانواده با باکس لینک‌های دانلود | تفکیک بصری از توضیحات + جلب توجه کاربری که فقط متن ترانه می‌خواهد |
| خوانایی | `font-size: 15px` · `line-height: 2.15` · محدودشدن عرض طبیعی کارت · فاصلهٔ بندها | متن ترانه خط‌کوتاه است؛ فاصلهٔ خطی کم، خواندن را خسته‌کننده می‌کند |
| لینک داخلی خواننده | چیپ «سایر آهنگ‌های {artist}» → ترم `singer` یا برچسب هم‌نام | تقویت ارتباط موجودیت خواننده و توزیع اعتبار داخلی |
| دکمهٔ «کپی متن ترانه» | `navigator.clipboard` + بازخورد «کپی شد» + پنهان‌شدن خودکار در مرورگرهای قدیمی | کاربران متن ترانه را در واتساپ/تلگرام می‌فرستند؛ این کار نرخ تعامل و بازگشت را بالا می‌برد |
| داده‌ساختاریافته | JSON-LD با گراف `MusicRecording` + `MusicComposition` (+ `audio` از `music320`/`music128`) و `lyrics` به‌صورت `CreativeWork.text` | درک موجودیت برای گوگل و به‌ویژه گراندینگ مدل‌های هوش مصنوعی |
| `lang="fa"` و `dir="rtl"` | روی خود باکس | کمک به تشخیص زبان و کیفیت استخراج متن توسط سیستم‌های چندزبانه |
| پشتیبانی از هر دو نوع فیلد | اگر مقدار HTML باشد → `wp_kses_post`؛ اگر متن ساده باشد → `esc_html` + `nl2br` | فیلد فعلی ویرایشگر (WYSIWYG) است؛ اگر روزی به Textarea تغییرش دهید، باز هم درست کار می‌کند |
| سوئیچ جای باکس | `$taranehyar_lyrics_position = 'here'` یا `'end'` | بدون جابه‌جا کردن کد، بالای پخش‌کننده یا پایین لینک‌های دانلود |
| سوئیچ اسکیما | `$taranehyar_lyrics_schema = true/false` | اگر افزونهٔ سئو خودش اسکیمای موسیقی می‌دهد، خاموشش کنید |
| حالت شب و موبایل | `.night .music_lyrics_box` و مدیای زیر ۷۶۸px | قالب تم تاریک دارد و ترافیک موبایل بالاست |

نمونهٔ خروجی داده‌ساختاریافته (خلاصه‌شده):

```json
{
  "@context": "https://schema.org",
  "@graph": [
    { "@type": "MusicRecording", "@id": "https://site/song/#recording", "name": "نام آهنگ",
      "byArtist": { "@type": "Person", "name": "نام خواننده" },
      "audio": { "@type": "AudioObject", "contentUrl": "…320.mp3", "encodingFormat": "audio/mpeg" },
      "datePublished": "…", "dateModified": "…", "recordingOf": { "@id": "…#composition" } },
    { "@type": "MusicComposition", "@id": "https://site/song/#composition", "name": "نام آهنگ",
      "lyricist": { "@type": "Person", "name": "نام خواننده" },
      "lyrics": { "@type": "CreativeWork", "text": "متن ترانه…", "inLanguage": "fa-IR" } },
    { "@type": "WebPage", "@id": "https://site/song/#webpage", "mainEntity": { "@id": "…#recording" } }
  ]
}
```

> نکتهٔ فنی: `lyrics` در schema.org از نوع **CreativeWork** است (نه Text خام)، پس ساختار `{"@type":"CreativeWork","text":"…"}` را گذاشتم که هم با دامنهٔ رسمی می‌خواند و هم مثال‌های خود schema.org.
> نکتهٔ امنیتی: JSON با `wp_json_encode` و بدون `JSON_UNESCAPED_SLASHES` تولید می‌شود تا اگر متن ترانه شامل `</script>` بود، نتواند از تگ اسکریپت بیرون بزند.

## ۴) بررسی UX (تجربهٔ کاربری)

**چیزهایی که درست شد**

| مساله | قبل | بعد |
|---|---|---|
| پیدا کردن متن | یک تودهٔ متن وسط صفحه بدون عنوان | هدر مشخص + آی‌کون + تیتر بزرگ‌تر از متن |
| خطای «کدام متن، مربوط به کدام آهنگ؟» | هیچ | نام آهنگ و خواننده در همان تیتر، با رنگ تأکیدی روی نام آهنگ |
| عبور از متن ترانه برای رسیدن به دانلود | اجتناب‌ناپذیر (متن بی‌شکل بود) | باکس، طول مشخص و قابل تشخیص دارد؛ کاربر سریع تصمیم می‌گیرد عبور کند یا بخواند |
| کپی کردن متن | دستی از مرورگر | یک دکمه با بازخورد «کپی شد» |
| رفتن به صفحهٔ خواننده | فقط از طریق تگ/سایر آهنگ‌ها | چیپ مستقیم در هدر باکس |
| خوانایی در موبایل | اندازه و فاصلهٔ خط ثابت دسکتاپ | کوچک‌تر شدن پدینگ/فونت + چیدمان عمودی هدر در موبایل |
| تم تاریک | متن سفید ساده | کارت تیره با حاشیهٔ ملایم و دکمه‌های هماهنگ |

**انتخاب‌های عامدانه و دلیلشان**

- **خط‌ها وسط‌چین مانده‌اند** (`text-align:center`) چون معادل قبلی `.music_textss` همین بود و تغییر ناگهانی، ظاهر سایت را برای کاربر فعلی غریبه می‌کند. اگر «راست‌چین» را ترجیح می‌دهید، فقط همین یک مقدار در `.music_lyrics_text` را عوض کنید (برای ترانه‌های با خط‌های بلند، راست‌چین واقعاً خواناتر است).
- **بدون اسکرول داخلی و بدون «بیشتر بخوانید»ِ مخفی به‌صورت پیش‌فرض.** متن داخل کادر اسکرول‌دار، در موبایل آزاردهنده است و پنهان‌کردن متن با `display:none` هم به استخراج‌پذیری آسیب می‌زند. اگر ترانهٔ خیلی بلند دارید، در بخش ۸ حالت تاشو را گذاشتم.
- **بدون انیمیشن ورود پرمشغله** در باکس متن؛ فقط کاور افکت دارد. متن ترانه محتوای خواندنی است، نه عنصر تزئینی.

**پیشنهادهای UX که هنوز پیاده نشده (اختیاری)**

- یک لینک کوچک «متن ترانه ⤵» کنار عنوان نوشته که با انکر `#taranehyar_lyrics_title` مستقیم به باکس بپرد — کاربر با قصد «متن» یک کلیک از دانلود‌کننده جدا می‌شود، بدون اینکه جای باکس را عوض کنیم.
- اگر دیسکوس بالا رفت: «بازگشت به دانلود ⤴» انتهای باکس.
- شمارندهٔ «تعداد بند/خط» در هدر (تزئینی؛ ارزش سئویی ندارد).

## ۵) بررسی SEO

**چیزهایی که واقعاً اثر دارند (و انجام شد)**

1. **تطبیق تیتر با الگوی جست‌وجو**: «متن آهنگ X از Y»، «متن آهنگ X»، «متن ترانه X» — تیتر ما هر سه را با یک عبارت پوشش می‌دهد (`متن آهنگ` + نام آهنگ + `از` + نام خواننده). این قوی‌ترین سیگنال درون‌صفحه‌ای برای این نوع صفحه است.
2. **سلسله‌مراتب هدینگ**: قبلاً صفحه فقط H1 (عنوان) داشت و بعد یک‌راست H3 برای بخش‌های جانبی؛ حالا H2 واقعی برای بخش اصلی محتوا داریم.
3. **`lang`/`dir` روی محتوا**: کمک به تشخیص زبان و برجسته‌سازی بخش فارسی.
4. **لینک داخلی به صفحهٔ هنرمند**: خزنده و مدل زبانی، «خواننده ← آهنگ» را به‌عنوان یک ارتباط موجودیتی می‌فهمد.
5. **ساختار خط‌به‌خط حفظ می‌شود** (`<p>` و `<br>` در نمایش، `\n` در متن اسکیمای `lyrics`): متن قابل قطعه‌بندی و استخراج است.
6. **`dateModified`** در اسکیما: برای صفحات متن ترانه که مرتب اصلاح می‌شوند، سیگنال تازگی مفیدی است.

**چیزهایی که اثر ندارند — انتظار واقع‌بینانه داشته باشید**

- **ریچ‌رزالت متن ترانه وجود ندارد.** گوگل برای lyrics ریچ‌رزالت تعریف نکرده؛ پس از این اسکیما نباید انتظار ظاهر خاص در SERP داشته باشید. ارزشش، درک موجودیت + شانس بیشتر استناد در پاسخ‌های هوش مصنوعی است.
- **FAQPage هم دیگر ریچ‌رزالت نمی‌دهد.** گوگل از ۷ مه ۲۰۲۶ این ریچ‌رزالت را کامل حذف کرد (از آگوست ۲۰۲۳ فقط برای سایت‌های دولتی/سلامت محدود شده بود). خودِ تایپ `FAQPage` باطل نشده و موتورهای دیگر/AI هنوز آن را می‌خوانند، اما **برای گرفتن ظاهر بیشتر در گوگل ارزشی ندارد.** پس سؤال‌های الکی نسازید.
- **متن تکراری**: این متن در ده‌ها سایت دیگر هم هست. جریمه‌ای برایش وجود ندارد، اما شانس رتبه‌گرفتنِ صرفاً با متن ترانه کم است. برندهٔ صفحه، همان چیزی است که فقط شما دارید: فایل صوتی، کیفیت‌ها، توضیحات اختصاصی و صفحهٔ خواننده. به همین دلیل **جای باکس را پیش‌فرض همان بالا نگه داشتم ولی قابل انتقال کردم.**
- **متنی که فقط برای کلمات کلیدی نوشته شده باشد** («بهترین سایت متن آهنگ فلان…») نه تنها کمکی نمی‌کند، بلکه کیفیت صفحه را پایین می‌آورد. یک خط توضیح طبیعی کافی است؛ متن ترانه خودش محتوای اصلی است.

**پیشنهاد بعدی سئویی (آمادهٔ کپی، هنوز اعمال نشده):** تیتر برای باکس دانلود. کاربر «دانلود آهنگ X از Y» را جست‌وجو می‌کند ولی الان آن بخش هیچ تیتری ندارد:

```php
<h2 class="dl_title">دانلود آهنگ <?php echo esc_html( $taranehyar_song ); ?> از <?php echo esc_html( $taranehyar_artist ); ?></h2>
```

این را قبل از `<div class="dl_links_box">` بگذارید (با همان متغیرهای `$taranehyar_song`/`$taranehyar_artist` که در باکس ترانه ساختیم) — هر دو قصد جست‌وجو (متن/دانلود) تیتر اختصاصی خودشان را می‌گیرند بدون تکراری‌شدن.

## ۶) بررسی GEO و AIO (بهینه‌سازی برای موتورهای مولد و هوش مصنوعی)

**واقعیت کلیدی:** ابزارهای AI (و ریپورت‌های ۲۰۲۵–۲۰۲۶ روی آن‌ها) عمدتاً **بدنهٔ HTML رندرشده** را می‌خوانند، نه JSON-LD را. یعنی برای AIO، *قابلِ‌دیدن بودن و تمیز بودن متن* مهم‌تر از اسکیمای اضافه است. کاری که باکس ما می‌کند دقیقاً همین است: متن به‌صورت متن واقعی، با تیتر صریح، در ابتدای مسیر خزیدن.

| سیگنال GEO/AIO | وضعیت در این پیاده‌سازی | چرا مهم است |
|---|---|---|
| تیتر پرسش‌مانند و صریح | ✅ `متن آهنگ {song} از {artist}` | مدل باید بتواند «این صفحه جواب کدام پرسش است» را در یک نگاه تشخیص دهد |
| Text در DOM (نه تصویر/کانواس/JS-only) | ✅ PHP چاپ می‌کند، بدون نیاز به اجرای JS | خزنده‌های AI اغلب JS اجرا نمی‌کنند |
| سیگنال زبان | ✅ `lang="fa" dir="rtl"` + `inLanguage: fa-IR` | استخراج و ترجمه‌سازی درست‌تر |
| نام‌گذاری یکدست موجودیت | ✅ نام آهنگ/خواننده در تیتر، چیپ لینک و اسکیما یکسان نوشته می‌شوند | «هم‌مرجعی موجودیت» (entity resolution) |
| خط‌بندی ساختاری متن | ✅ `<p>`/`<br>` در نمایش و `\n` در `lyrics.text` | مدل می‌تواند ترانه را بخش‌بخش نقل کند، نه یک تودهٔ گیج |
| داده‌ساختاریافتهٔ اتصال‌دهنده | ✅ گراف `MusicRecording` ↔ `MusicComposition` ↔ `WebPage` با `@id` یکتا | گراندینگ و اتصال به گراف دانش |
| تازگی | ✅ `dateModified` | صفحات ترانه مرتب اصلاح می‌شوند؛ AI ترجیح می‌دهد نسخهٔ به‌روز را نقل کند |
| اجازهٔ خزیدن AI | ⚠️ تصمیم شما (robots.txt) | اگر GPTBot/PerplexityBot/Google-Extended/ClaudeBot را ببندید، استناد در پاسخ‌ها عملاً صفر می‌شود — ولی اگر می‌خواهید ترافیک فقط وارد سایت شود و متن برداشت نشود، بستن هم گزینهٔ مشروعی است |

**تصمیم‌های استراتژیکی که باید خودتان بگیرید**

1. **کدام حالت را می‌خواهید: «همه‌جا نقل شویم» یا «ترافیک مستقیم»؟** اگر هدف، دیده‌شدن برند در پاسخ‌های AI است، اجازهٔ خزیدن + متن تمیز + تیتر صریح را بدهید و از دکمهٔ کپی و لینک خواننده (که سایت شما را منبع می‌کند) فایده بگیرید. اگر هدف فقط ترافیک ارگانیک است، ممنوع‌کردن خزنده‌های AI منطقی است — اما در پاسخ‌های AI به‌جای شما، سایت‌های رقیب نقل خواهند شد.
2. **`llms.txt`**: یک پیشنهاد در حال شکل‌گیری است و هیچ موتور بزرگی تعهدی به آن نداده؛ اگر خواستید می‌توانید اضافه کنید، اما **روی آن حساب باز نکنید.** ساختار HTML همین صفحه مهم‌تر است.
3. **نقل‌قول‌پذیری**: اگر می‌خواهید مدل‌ها همان جملهٔ شما را ورد کنند، یک جملهٔ کوتاه و «خودبسنده» بالای متن ترانه (مثلاً نام کامل آهنگ + خواننده + سال انتشار در یک قالب واحد) بیشترین کمک را می‌کند. صرفاً به‌شرطی که برای کاربر هم مفید باشد؛ جملهٔ تبلیغاتی گنده کمک نمی‌کند.

## ۷) ریسک‌ها و هشدارها

| ریسک | توضیح | راه‌حل |
|---|---|---|
| حق نشر متن ترانه | بازنشر کامل ترانه در بسیاری از حوزه‌ها مجوز لازم دارد؛ این پروژه هم از ابتدا «وضعیت مجوز نامشخص» داشته و این تغییر آن را حل نمی‌کند | در نوشتهٔ داخلی سیاست مشخص کنید (منبع‌دهی، ارسال توسط کاربر، مجوز)؛ در صورت لزوم فقط بخش کوتاه (کوپلهٔ اول) منتشر کنید |
| تضاد اسکیما با افزونهٔ سئو | اگر Yoast/Rank Math اسکیمای صفحه را می‌سازد، اسکیمای ما موازی با آن کار می‌کند؛ تداخلی که خطا بدهد معمولاً رخ نمی‌دهد چون `@id`ها یکتا هستند، اما ممکن است دو روایت مختلف از یک صفحه در یک صفحه باشد | اگر افزونه اسکیمای موسیقی ندارد (پیش‌فرض ندارد) این را نگه دارید؛ اگر روزی خواستید فقط `MusicRecording` بماند، `$taranehyar_lyrics_schema = false` |
| حجم JSON-LD | متن کامل ترانه در اسکیما هم تکرار می‌شود (چند کیلوبایت اضافه) | قابل چشم‌پوشی است؛ برای کاهش، در کد می‌توانید فقط بند اول را در `lyrics.text` بگذارید |
| فیلد `music_text` ویرایشگر است | خطوطی که با `Shift+Enter` شکسته نشوند، در HTML به `<p>` تبدیل می‌شوند و بندبندی ترانه ممکن است درست نباشد | در ACF برای این فیلد تیتر/راهنما بگذارید: «هر خط ترانه یک سطر، بین بندها یک سطر خالی»؛ کد ما هم متن ساده و هم HTML را می‌فهمد |
| کلمات کلیدی در متن aria | `aria-label="کپی متن ترانه"` یک برچسب دسترس‌پذیری است، نه کانال سئو | انتظار سئویی از آن نداشته باشید (و برای «کپی متن» فایدهٔ واقعی دسترسی‌پذیری دارد) |

## ۸) چک‌لیست اقدام‌های اختیاری

| کار | ارزش | یادداشت |
|---|---|---|
| تیتر H2 برای باکس دانلود (بخش ۵) | ★★★ | به‌همراه باکس ترانه، هر دو قصد جست‌وجو تیتر اختصاصی می‌گیرند |
| `inAlbum` / `duration` / `genre` در اسکیما | ★★ | اگر فیلد نام آلبوم و مدت‌زمان دارید، ارتقای خوبی است (`duration` باید فرمت ISO 8601 مثل `PT3M42S` باشد) |
| `sameAs` (ویکی‌پدیا/موزیک‌برینز هنرمند) | ★★ | قوی‌ترین سیگنال «موجودیت واقعی» برای GEO؛ نیاز به نگهداری داده دارد |
| حالت تاشو برای ترانه‌های بلند | ★ | `<details>` را زیر `<section>` بگذارید و متن داخلش را نگه دارید؛ برای AI هم متن در DOM می‌ماند |
| انکر «متن ترانه ⤵» کنار عنوان | ★★ | کمک به UX هر دو گروه کاربر، بدون تغییر جای باکس |
| بستن/بازکردن خزنده‌های AI در robots.txt | ★★ | تصمیم سیاستی، نه فنی |
| `speakable` / پخش صوتی متن ترانه | ✗ | برای این نوع صفحه ارزش عملی ندارد |

## ۹) چطور تست کنیم (روی staging)

1. یک نوشتهٔ آهنگ با `music_text` پر و `song`/`artist` پر باز کنید و **View Source** بگیرید: باید `section.music_lyrics_box`، تیتر H2 با نام آهنگ/خواننده و یک `<script type="application/ld+json">` ببینید.
2. `JSON-LD` را در **Schema Markup Validator** (validator.schema.org) بگذارید → باید بدون خطا `MusicRecording` و `MusicComposition` را نشان دهد.
3. **Google Rich Results Test** → انتظار هیچ آیتم میوه‌ای نداشته باشید (طبیعی است)؛ فقط نبودِ خطای ساختاری مهم است.
4. در Search Console، کوئری‌های «متن آهنگ …» را دنبال کنید (چند هفته) و نرخ کلیک صفحه را قبل/بعد مقایسه کنید.
5. تست AI: در ChatGPT/Perplexity/Gemini بپرسید «متن آهنگ {song} از {artist}» و ببینید از دامنهٔ شما استناد می‌شود یا نه (این تست فقط نشانه است، نه معیار قطعی).
6. موبایل، حالت شب، و دکمهٔ کپی را در مرورگر واقعی امتحان کنید.
